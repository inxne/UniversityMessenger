# Шпаргалки к защите проекта

Вопросы, которые могут задать на защите, и короткие ответы на них.
Файл пополняется на каждом шаге разработки.

## Архитектура

В: Почему код разбит на Core, Console и Server?
О: Ядро хранит логику и не знает, кто его вызывает. Консоль и сервер — два разных способа вызвать одно и то же ядро. Это слоистая архитектура: модели, хранилище, сервисы, точки входа.

В: Зачем интерфейс IStorage, если реализация одна?
О: Это контракт. Сервисы зависят от него, а не от конкретной реализации. Позже мы заменим InMemoryStorage на базу данных SQLite, не тронув ни одного сервиса.

В: Что такое внедрение зависимостей в вашем коде?
О: Сервисы не создают хранилище через new, а получают его через конструктор. Сервер регистрирует всё в контейнере зависимостей, и фреймворк сам собирает объекты.

В: Почему Singleton?
О: Один экземпляр хранилища на всё приложение. Иначе каждый запрос получал бы свою пустую память, и пользователи не видели бы друг друга.

## Модели данных

В: Зачем роли сделаны перечислением, а не строками?
О: Перечисление типобезопасно: невозможно написать роль с опечаткой и получить некорректного пользователя.

В: Почему в User нет поля Password?
О: Пароль не хранится. Хранится только PasswordHash, результат одностороннего преобразования BCrypt. Проверка при входе идёт через BCrypt.Verify.

В: Зачем поле FullNameLower?
О: Денормализация для поиска без учёта регистра: запрос приводим к нижнему регистру и ищем подстроку в FullNameLower.

В: Что такое DirectKey?
О: Ключ личного чата из двух Id участников, отсортированных по возрастанию. Пара людей в любом порядке даёт один ключ, поэтому второй личный чат между теми же людьми создать невозможно.

В: Зачем ChatMember, если есть Chat?
О: Это связка многие-ко-многим: кто состоит в каком чате и с какой ролью внутри чата. Роль в чате не равна роли в системе: студент может быть владельцем группы.

В: Зачем DeletedAt вместо удаления сообщения?
О: Мягкое удаление: история сохраняется, сообщение помечается удалённым. Это нужно для аудита и восстановления.

## Сервисы и ошибки

В: Зачем свой тип AppException?
О: Отделить бизнес-ошибки (короткий пароль, чужой чат) от системных сбоев. Сервер ловит AppException и превращает его в код 400 или 401 с русским сообщением.

В: Где проверяется право писать в чат?
О: В ChatService.SendMessage: перед сохранением проверяется участие отправителя в чате. Обойти это через API невозможно.

В: Чем 400 отличается от 401?
О: 400 — запрос понят, но данные нарушают правила. 401 — не подтверждена личность. Клиент по коду отличает ошибку формы от ошибки входа.

## Сервер и HTTP

В: Почему минимальные API, а не контроллеры?
О: Эндпоинты объявляются прямо в Program.cs через MapGet и MapPost. Для небольшого API это короче и нагляднее, бизнес-логика при этом живёт в Core.

В: Зачем UserDto, если есть User?
О: Контракт наружу не содержит PasswordHash. Хеш пароля физически не может уехать клиенту.

В: Что означает {chatId:guid} в маршруте?
О: Ограничение маршрута: сегмент принимается только если он корректный Guid. Мусорные адреса отклоняются до входа в обработчик.

В: Чем path отличается от query и body?
О: path — часть адреса в фигурных скобках маршрута. query — параметры после знака вопроса. body — данные запроса в JSON. В одном запросе бывает только одно body.

В: Зачем SenderName прямо в MessageDto?
О: История приходит одним запросом с готовыми именами отправителей, клиент не делает серию дополнительных запросов.

В: Почему данные исчезают после перезапуска сервера?
О: Хранилище InMemoryStorage живёт в оперативной памяти. Это осознанный компромисс этапа, мотивация следующего шага — база данных SQLite.

## Инструменты и процесс

В: Зачем Swagger?
О: Автогенерируемая страница документации API, где можно вызывать эндпоинты прямо из браузера и видеть ответы. Удобно для тестов без клиента.

В: Как устроена страховка проекта?
О: Коммит после каждого шага, push на GitHub в конце сессии. Плюс журнал изменений changelog.md и карта архитектуры architecture.md в репозитории.

## Аутентификация JWT (шаг С4)

В: Что такое JWT простыми словами?
О: Подписанная сервером записка с данными пользователя (Id, почта, роль) и сроком действия. Сервер не хранит сессии, а проверяет подпись при каждом запросе.

В: Почему из запросов исчезли userId и senderId?
О: Идентификатор берётся из токена. Клиент больше не может назвать себя чужим Id, поэтому чтение чужих чатов невозможно.

В: Где хранится секретный ключ подписи?
О: В учебном проекте в appsettings.json, секция Jwt. В бою ключ выносится в переменные окружения или секретное хранилище.

В: Что сервер проверяет у токена?
О: Подпись, издателя, адресата и срок действия. Любое несоответствие означает отказ 401.
