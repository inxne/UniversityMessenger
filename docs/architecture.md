# Карта архитектуры: все файлы проекта и их назначение

## UniversityMessenger.Core — ядро системы

### Папка Models — данные

#### Models/Role.cs
- Внутри: перечисление Role (Student, Teacher, Admin).
- Зачем: роли пользователей как типобезопасный тип вместо строк.
- Для защиты: роли моделируются перечислением, исключены опечатки в значениях.

#### Models/User.cs
- Внутри: класс User: Id, Email, PasswordHash, FullName, FullNameLower, Role, Faculty, Course, About, IsVerified, IsActive, CreatedAt, ConsentAt.
- Зачем: центральный профиль пользователя.
- Для защиты: пароль хранится только как хеш; FullNameLower даёт поиск без учёта регистра; ConsentAt фиксирует согласие на персональные данные.

#### Models/ChatType.cs
- Внутри: перечисление ChatType (Direct, Group).
- Зачем: различие личных и групповых чатов с разными правилами создания.

#### Models/Chat.cs
- Внутри: класс Chat: Id, Type, Name, DirectKey, CreatedByUserId, CreatedAt.
- Зачем: сущность переписки.
- Для защиты: DirectKey из двух отсортированных Id гарантирует один личный чат на пару людей.

#### Models/ChatMember.cs
- Внутри: перечисление ChatMemberRole (Member, Admin, Owner) и класс ChatMember: Id, ChatId, UserId, MemberRole, JoinedAt.
- Зачем: связка многие-ко-многим между пользователями и чатами плюс роль внутри чата.
- Для защиты: роль в чате отделена от роли в системе: студент может владеть группой.

#### Models/Message.cs
- Внутри: класс Message: Id, ChatId, SenderId, Text, CreatedAt, DeletedAt.
- Зачем: сообщение переписки.
- Для защиты: мягкое удаление через DeletedAt сохраняет историю.

### Папка Storage — где лежат данные

#### Storage/IStorage.cs
- Внутри: интерфейс IStorage, контракт методов доступа к данным.
- Зачем: сервисы зависят от контракта, а не от реализации.
- Для защиты: подмена хранилища (память на базу) не требует правок сервисов.

#### Storage/InMemoryStorage.cs
- Внутри: реализация IStorage на четырёх списках в памяти.
- Зачем: быстрое рабочее хранилище для демо и тестов сервера.
- Для защиты: осознанный компромисс этапа до подключения SQLite; данные исчезают при перезапуске.

### Папка Services — правила и логика

#### Services/AppException.cs
- Внутри: класс AppException, наследник Exception с русским сообщением.
- Зачем: единый тип бизнес-ошибок.
- Для защиты: бизнес-ошибки отделены от системных сбоев; сервер маппит их в коды 400 и 401.

#### Services/AuthService.cs
- Внутри: методы Register, Login, GetById.
- Зачем: регистрация с проверками, хеширование пароля BCrypt, вход со сверкой хешей, проверка блокировки.
- Для защиты: пароль не хранится и не сравнивается в открытом виде.

#### Services/UserService.cs
- Внутри: метод Search с необязательными фильтрами.
- Зачем: поиск активных пользователей по ФИО без учёта регистра, фильтры по роли, факультету, курсу.
- Для защиты: поиск по денормализованному FullNameLower не зависит от регистра запроса.

#### Services/ChatService.cs
- Внутри: GetOrCreateDirectChat, CreateGroupChat, SendMessage, GetHistory, GetChatsOfUser, GetChatTitle, приватный MakeDirectKey.
- Зачем: вся логика переписок и проверок участия.
- Для защиты: проверка участия на уровне сервиса делает запись в чужой чат невозможной через API.

## UniversityMessenger.Console — демо ядра

#### Program.cs
- Внутри: сценарий из семи частей: сборка сервисов, регистрация троих, вход, проверка ошибки, поиск, личный чат, группа, история, список чатов.
- Зачем: интеграционный прогон всей логики без сервера.
- Для защиты: демо выступает сценарием проверки всех сервисов вместе.

## UniversityMessenger.Server — сервер API

#### Program.cs
- Внутри три слоя:
  1. Регистрация зависимостей: IStorage, AuthService, UserService, ChatService, Swagger.
  2. Эндпоинты: GET /api/health, POST /api/auth/register, POST /api/auth/login, GET /api/users.
  3. Контракты: record RegisterRequest, LoginRequest, UserDto без PasswordHash.
- Зачем: превращает логику ядра в HTTP API для будущего клиента.
- Для защиты: сервер тонкий, бизнес-правил не содержит, вся логика в Core.

## Файлы, которые не наши

В папках obj и bin есть сгенерированные компилятором .cs файлы. Они не видны в редакторе, не правятся руками и не попадают в git благодаря .gitignore.

## Схема связей

Server/Program.cs принимает HTTP и вызывает сервисы.
Console/Program.cs вызывает те же сервисы напрямую.
Сервисы принимают решения и работают с данными через IStorage.
InMemoryStorage реализует IStorage и хранит модели.
Модели знают только про себя.

## Правило слоёв

Модели знают только про себя.
Хранилище знает, где лежат модели.
Сервисы знают правила и работают с хранилищем через интерфейс.
Сервер и консоль вызывают сервисы, каждый своим способом.
